## PoC-01/02 — DWM 썸네일

| 원본 상태 | 썸네일 | 갱신 |
|---|---|---|
| 표시 | 보임 | 실시간 |
| 다른 창에 가림 | 보임 | 실시간 |
| 최소화 | 보임 | **정지(마지막 프레임)** |
| `SW_HIDE` | 보임 | **정지(마지막 프레임)**, 45초 유지 확인 |
| 화면 밖 이동 | 보임 | 정지 |

- **대상 창 종류:** 일반 팝업, `LWA` 레이어드, **`UpdateLayeredWindow` 레이어드(계획한 더미 표면 방식)** 모두에서 썸네일이 표시된다.
- **리소스:** 등록/해제 500회에 걸리는 시간은 회당 0.1 ms이고, 핸들·GDI·USER 객체 증가는 0이다.
- **UWP 계산기:** 하네스 창과 동일하게 숨김 상태에서도 정지 화면이 유지된다.
- **의미:**
  - 명세의 `FOLDED_LIVE`(숨긴 창의 실시간 미리보기)는 **불가능**하다. 숨기면 갱신이 멈춘다.
  - 반대로 DWM이 **마지막 프레임을 무료로 들고 있다.** 우리 프로세스는 GPU 메모리를 쓰지 않고, 캡처 테두리도 없으며, 접는 데 걸리는 시간은 0.1 ms 수준이다. → 아래 '설계 반영 제안 1' 참고

## PoC-03 — WGC 스냅샷

| 항목 | 하드웨어 GPU | WARP(소프트웨어) |
|---|---|---|
| 디바이스 생성 | 134~184 ms | **5~12 ms** |
| 창 1개: 준비(CreateForWindow+세션) | 68~94 ms | 71~126 ms |
| 창 1개: 첫 프레임 | 6~21 ms | 8~68 ms |
| 창 1개: 픽셀 준비 완료(합계) | 81~107 ms | 95~138 ms |
| 창 5개 동시: 픽셀 준비 완료 | 197 ms | 173 ms |
| 2560×1032 큰 창 | 87 ms | 99 ms |
| 메모리 증가(캡처 중) | **+43~57 MB** | **+1.5 MB** |
| 디바이스 해제 후 | 원래 수준으로 복귀 | 원래 수준으로 복귀 |

- **실패 경우:** 최소화된 창과 `WDA_EXCLUDEFROMCAPTURE` 창은 **프레임이 오지 않는다**(1초 타임아웃). 아이콘 카드 폴백이 필요하다는 점이 확인됐다.
- **Win11 테두리:** 노란 테두리 제거(Borderless) 요청이 허용됐다.
- **의미:**
  - 시간의 대부분은 **캡처 세션 준비(약 70~120 ms)**이고 첫 프레임은 빠르다.
  - 캐시 없이 창 10개를 한 번에 접으면 300 ms 목표를 넘는다. 사전 캡처나 DWM 경로가 필요하다.
  - WARP는 지연이 비슷하면서 메모리 증가가 1/30 수준이다. **저사양 기본값으로 WARP가 유리하다.**

## PoC-04 — 복구 저널 + 감시자

| 시나리오 | 결과 |
|---|---|
| 창 3개 숨김 → 매니저 `TerminateProcess` | 감시자가 **31 ms** 안에 3개 모두 복구 |
| 가짜 항목(같은 HWND인데 생성 시각 다름 / 없는 HWND) | 2건 모두 **복구 거부** (잘못된 앱에 명령 안 보냄) |
| 정상 종료 | 매니저가 직접 복원하고 저널에 clean 표시 → 감시자는 아무것도 안 함 |
| 매니저 + 감시자 둘 다 강제 종료 | 창이 숨김 상태로 남음(예상대로) → 다음 실행 시 `recover`로 108 ms 만에 복구 |
| 저널(창 30개, 5KB) 쓰기 | flush 생략 시 평균 3.6 ms / P95 5.0 ms, flush 포함 시 평균 5.2 ms / P95 6.5 ms (NVMe) |
| 1바이트 손상 | 체크섬이 감지 |

- 계획서 '조정 ①'(flush 생략)의 근거가 유지된다. 프로세스 크래시 후에도 OS 캐시의 저널을 정상적으로 읽었다. HDD에서의 flush 비용은 PoC-06에서 측정한다.

## PoC-05 — 창 끌기 감지 + 놓는 곳 바

| 시나리오 | 결과 |
|---|---|
| A. 창을 끌어 바에 놓기 | 바 표시 ✅, **끌리는 창 위에 바가 실제로 보임**(화면 샘플링) ✅, 놓기 감지 ✅ |
| B. 끄는 중 `Esc` | 바가 떴다가 취소 감지(시작 위치로 복귀) ✅, 놓기 처리 안 됨 ✅ |
| C. 3px 살짝 끌기 | OS가 이동 루프를 시작하지 않아 이벤트 자체가 없음 → 바 안 뜸 ✅ |
| D. 모서리로 크기 조절 | 크기 조절로 판정하고 바 안 뜸 ✅ |
| E. 일반 이동(바 밖에 놓기) | 바는 뜨지만 놓기 처리 안 됨 ✅ |
| 대기 비용 | 10초 동안 CPU 0~15.6 ms(측정 단위 한계), 사이클 0.8M, 훅 이벤트 0건, working set 6.5 MB |

- `WH_MOUSE_LL`이나 DLL 주입 없이 `SetWinEventHook`만으로 충분하다는 점을 하네스 창에서 확인했다.

## 설계 반영 제안 (계획서 변경 필요 → 사용자 결정)

1. **미리보기 1순위를 "DWM 썸네일 정지 화면"으로 변경하고, WGC는 폴백으로 둔다.**
   - 근거: PoC-02에서 숨긴 창의 마지막 프레임이 유지됐다. 접기 지연, GPU 메모리, Win10 노란 테두리 문제가 모두 사라진다.
   - 안전장치:
     - 접은 직후 우리 더미 영역을 1회 화면 샘플링해 "실제로 보이는지" 자체 검증한다. 명세가 금지한 'HRESULT만 믿기'를 피하기 위해서다.
     - 검증에 실패하면 미리 떠 둔 WGC 스냅샷을 쓰고, 그것도 없으면 아이콘 카드를 쓴다.
   - 남은 위험: Chrome, Office처럼 GPU 스왑체인을 쓰는 앱은 숨겼을 때 결과가 다를 수 있다. 메모리가 부족할 때 DWM이 정지 프레임을 버리는지도 아직 모른다. → 실제 앱 검증 필요.
2. **WGC 캡처 디바이스의 기본값을 WARP로 한다.** 메모리 +1.5 MB 대 +43 MB이고 지연은 비슷하다. GPU 드라이버 품질과도 무관해진다.
3. **WGC 타임아웃은 '세션 준비 완료 후 150 ms'로 한다.** 최소화된 창과 캡처 방지 창은 시도하지 않고 바로 아이콘 카드로 처리해 접기 지연을 막는다.

## 남은 검증 (사용자 환경 필요)

1. **실제 앱:** Chrome/Edge(다중 창), Excel, Outlook, Windows Terminal, VS Code, 탐색기, 카카오톡.
   - 끌기 감지: `build\bin\Release\poc_drag.exe --seconds 60`을 실행하고 그 시간 동안 각 앱 창을 끌어 본다.
   - DWM/WGC: `poc_dwm.exe --hwnd 0x...`, `poc_wgc.exe --hwnd 0x...`. **이 도구들은 지정한 창을 잠깐 숨기므로, 저장하지 않은 작업이 없는 창으로만 실행한다.**
2. **PoC-06 저사양:** 저사양 기준기(예: Celeron N4020 / 4GB / HDD / Win10 22H2)에서 `powershell -ExecutionPolicy Bypass -File scripts\run_poc.ps1`를 실행한다.
3. **Windows 10 22H2:** 같은 스크립트로 측정한다. WGC 노란 테두리와 DWM 정지 화면 유지 여부를 확인한다.

## 개발 환경 메모

- 이 PC에서는 사용자 폴더 경로에 한글이 있으면 `vcvars64.bat`을 `.cmd`에서 호출할 때 경로 문제가 생기고, CMake Ninja 생성기의 컴파일러 감지가 `0xC0000409`로 종료된다.
- 그래서 빌드는 **Visual Studio 생성기**(`build.ps1`)를 쓴다. vcvars 환경이 필요 없다.
